# 导入模式（import）—— 在新工程执行

## 目标

用全新上下文把旧工程的成果对接到新工程，验证可用后再继续开发。顺序固定：先读后动，先验证后开发。

## 导入仪式（顺序执行）

1. `pwd`：确认当前在新工程根目录。`git status` + `git log --oneline -10`：了解新工程现状。
2. 定位迁移包：用户指定路径，或在当前目录/上级目录找 `migration-package/`、`MIGRATION.md`。
3. 读 `MIGRATION.md`：迁移范围、关键决策、遗留问题、差异预警、验证标准。
4. 读 `migration-map.json`：拿到全部迁移项及状态。
5. 逐项落地：
   - 按 `old_path → new_path` 复制文件；`new_path` 为空的按旧路径同款结构落地，有冲突时停下来问用户；
   - 路径/命名差异导致的引用修改（import 路径、include 路径、配置里的绝对路径），每处修改记入 MIGRATION.md 的"差异与决策"节——不静默改；
   - 落地一项就把 `migration-map.json` 中该项 `status` 改为 `done`，并填写实际 `new_path`。
6. 环境对齐：按 MIGRATION.md 的依赖清单安装/配置（版本不一致时记录决策）；密钥类按清单里的变量名提示用户自行配置，不索要密钥内容。
7. 跑验证标准里的基线验证：构建 + 测试 + 冒烟。通过的项在 `migration-map.json` 里把 `status` 改为 `verified` 并在 `evidence` 写证据（测试名/日志路径）。
8. `git add` + `git commit`：迁移成果一个描述性 commit（如 `migrate: import <范围> from <旧工程>`）。

## 汇报模板（写新代码前向用户汇报）

```
## 迁移结果
- 已落地并验证：N 项（列关键的）
- 已落地未验证：N 项（原因）
- 未落地/跳过：N 项（原因）

## 差异与决策
- 路径/依赖/版本差异处理：...

## 基线检查
- 构建：正常/异常
- 测试/冒烟：通过/失败（失败则先修基线）

## 计划
- 旧工程遗留的下一步：...
- 我准备先做：...
- 请确认或调整。
```

## 规则

- 汇报并得到用户确认前，不写迁移范围以外的新代码。
- 迁移包与旧工程聊天记录冲突时，以迁移包为准；迁移包缺失/不全时，从旧工程文件与 git log 推断，并向用户说明假设，不假装确定。
- 验证不通过的项保持 `status: done`（或回退 `pending`），绝不置 `verified`；只有实际验证过才置 `verified`。
- 基线异常：先修基线再开始新功能，不带坏基线叠功能。
- 迁移完成后提醒用户：旧工程可归档只读，后续开发只在新工程进行，避免两边漂移。
