# 导出模式（export）—— 在旧工程执行

## 目标

把"新工程接续开发所需的一切"落盘成迁移包，使一个零上下文的新 agent 只读迁移包就能完成对接。

## 1. 盘点迁移范围

先回答一个问题：**哪些东西搬到新工程，哪些留下？**

1. `git status` + `git diff --stat` + `git log --oneline -10`：确认未提交成果与最近历史，快照写进 MIGRATION.md。
2. 列出候选迁移项，分类：
   - **要迁**：源代码、配置、文档、测试、脚本、未提交的工作成果；
   - **不迁**：build 产物（`build/`、`sim_build/`、`dist/`）、依赖目录（`node_modules/`、`.venv/`）、IDE 缓存；
   - **禁止迁**：密钥、`.env`、凭证文件——只在新工程重建，不进迁移包；
   - **不确定**：问用户，不要替他决定。
3. 记录环境与依赖：语言/工具链版本、依赖清单（requirements / package.json / 环境变量名列表，只列名字不列值）、外部资源（EDA 工具、仿真器、许可证）。

## 2. 生成迁移包

默认位置：旧工程根的 `migration-package/`（用户可指定其他位置）。内容：

1. `MIGRATION.md`（复制 assets/templates/MIGRATION.md.tpl 填写）：
   - 迁移范围与理由（为什么迁、迁什么、不迁什么）；
   - 关键决策：影响新工程开发的判断，附文件引用；
   - 遗留问题：已知 bug、未完成项、flaky 测试；
   - 差异预警：新工程已知的不同点（目录结构、版本、命名）；
   - 验证标准：新工程里判断"迁移成功"的具体检查（构建命令、测试命令、预期结果）。
2. `migration-map.json`（复制 assets/templates/migration-map.json.tpl）：
   - 每个迁移项一条：`old_path`（旧工程相对路径）、`new_path`（新工程相对路径，可留空由 import 决定）、`status: pending`、`verify`（怎么验证这项迁对了）；
   - 目录级条目用 `old_path: "src/"` 表示整目录迁移，不要逐文件罗列几百条。
3. `files/`：按旧工程相对路径组织的待迁移文件副本；大工程可改为 tar/zip 归档，在 MIGRATION.md 里注明归档文件名与解包方式。

## 3. 导出自检

模拟新 agent 只读迁移包，应能回答：

1. 要迁哪些文件，分别放到新工程的哪里？
2. 哪些东西明确不迁？
3. 新工程需要什么环境与依赖才能跑起来？
4. 迁移完成后用什么命令/检查确认成功？
5. 旧工程有哪些未完成项和已知坑？

答不上来就补迁移包，直到能答上来为止。最后提醒用户：把迁移包复制/移动到新工程可访问的位置，并在新工程发起 import。
