# 设计流程规范

定位：**设计侧（RTL）专用的过程规范**——产出并维护设计相关文件
（叙事设计文档、`spec.yaml` 功能契约），随工程演进逐阶段补充。
配套关系：dv-collab 只定义设计/验证两侧的边界与交接契约格式；
`sim-flow`（验证侧维护）负责验证相关文件的产出。本 skill 内含
架构设计方法（§6）与 RTL 代码风格（§7），并管"设计动作流与
交付物（契约/功能点）的完整性与正确性"。

## 1. 契约先行的设计动作流

1. 架构/功能设计 → 叙事文档（`doc/md/`，方法按 §6）；
2. 从叙事文档**正向提取** `spec.yaml`（字段契约见 dv-collab
   `references/spec.md`）——功能点清单 = 文档的结构化目录，
   每条 FUNC/contract 用 `source` 字段回指文档条款（条款号/节号）；
3. RTL 以 yaml 功能点为**实现准绳**；禁止用 RTL 当前行为反写或删减
   契约（契约表达设计意图，不是实现快照）；
4. 行为任何变化：**先升版 yaml（version + change_summary），再改 RTL**；
   验证侧按版本 re-baseline 回归范围；
5. yaml 内容由设计侧手写；工具只做机械校验（schema 字段齐全、ID 唯一、
   引用闭合、条款↔FUNC 对照），不代替人写内容。

## 2. 阶段模型与过门（OpenTitan 模式）

阶段：L0 需求规格 → L1 开发 → L2 签核（裁剪到模块级）。四件套：

1. **准出检查单**：每个阶段门一张，分机检项（脚本可判）与评审项
   （人判），逐条给结论，不许静默跳过；
2. **独立提交过门**：每次过门 = 一次专门的 git 提交（不夹带其他
   改动），提交信息列检查单逐条结果与依据——评审即审查该提交；
3. **commit 锚定**：过门点在 `spec.yaml` 的 `doc` 区记录 `stage` 与
   `commit_id`，任何时刻可重建"哪版规格对应哪版代码"；
4. **审核分级（2026-08-19 用户定）**：**G1 为硬门，必须人审**，机检
   全过不豁免；**G2/G3 为软门，推荐人审**——过门时必须向用户
   **明确提问**"本门是否需要人工审核？"：需要则评审通过才过门；
   不需要则机检通过即过门。提问与用户的决定必须记入该次过门提交
   信息（防静默跳审）。

阶段状态机（记录在 `spec.yaml` `doc.stage`）：

```
draft ──G1──▶ req_confirmed ──G2──▶ arch_reviewed ──G3──▶ confirmed（交付验证侧）
 （G1 需求确认 / G2 架构评审 / G3 spec 签版；confirmed 后变化走升版流程）
```

### 阶段 0｜需求收集（L0，与设计人员对话）

- 动作：开工先检查工程骨架（dv-collab §2 定稿结构）：缺失则运行
  dv-collab/tools/init_project.py 创建（幂等，已存在跳过），并把
  design-flow/tools/ 机检脚本拷入工程 tools/（已存在且一致跳过，
  不一致报告由人处置，不静默覆盖）；设计人员提供设计功能（口述/草稿），
  按 §6 架构设计方法的
  结构化提问（只问缺的、给默认值、一次≤4 个）；
- 产物：叙事文档第一章"需求清单"：每条需求一个 REQ-id（REQ-001…）、
  来源、优先级；默认值/假设显式列出。REQ 嵌叙事文档，不单独建
  yaml；需求另有正式出处时 REQ-id 直接引用外部编号；功能提问与默认
  假设登记用 doc/md 下的 md 文档（如 功能提问.md）——可读形式、不做
  yaml 状态追踪，结论最终由 spec.yaml 吸收，不在 doc/yaml 建 question
  类文件；文档骨架按 references/功能说明模板.md 填写；
- 需求清单结构约束（树形功能分解，每层 MECE——不重不漏）：
  - 文档首节（需求清单之前）为"功能概述"：模块能做什么/要做什么
    的叙事描述（主功能、端到端行为、明确不做的事），不含实现细节；
    概述回答"这是什么"，需求清单回答"要满足什么"——需求清单 =
    验证需要感知的全部功能（含产生接口可观测行为的性能机制，如
    投机读/预取），只有纯内部实现细节才不进清单；
  - REQ 按树形功能分解组织：L0 = 模块一句话定义；L1 大类（3~7 个，
    行为上互相独立、合起来等于 L0）；大类内递归细分到小类（通路类
    建议按"受理→转换→执行→响应"流水阶段切），直到叶子；每个
    非叶节点带一句"本节点功能全集定义"，完备性审查 = 逐节点问
    "子类是否把父类说全"；每条 REQ 恰好归属一个叶子（他处需要时
    用文字引用，不重复挂）；空类显式写"无"，不许静默缺类；
  - L1 参考骨架（按设计形态裁剪）：接口与形态 / 写通路 / 读通路 /
    读写共享语义 / 管理面 / 观测面 / 性能与范围；
  - REQ-id 全局连续编号，不随分类或后续修订重排（保证评审期引用
    稳定）；
  - 每条 REQ 一行自含：id + 需求 + 来源 + 优先级（正文条款回指在
    阶段 1 补登）；
- **G1 准出检查单**：
  - 机检：每条 REQ 有 id/来源/优先级；无"等/若干/尽量"类模糊词；
    需求清单树形分解合规（非叶节点有全集定义句、每叶有导读、
    REQ 恰好挂一个叶子、空类显式写"无"）；
    假设清单存在且逐条有处置（确认/转 doc/md 功能提问文档）——
    机检脚本：tools/req_check.py；
  - 评审（**硬门，必须人审**）：设计人员确认默认值与假设——机检
    全过不豁免，人审通过才过门。

### 阶段 1｜架构设计（L0→L1，§6 架构设计方法全流程）

- 产物：架构设计文档（doc/md 单独成文，如 架构设计.md：方案对比+定量
  推导+模块划分，不并入功能说明；骨架按 references/架构设计模板.md
  填写）；
- **G2 准出检查单**：
  - 机检：分析检查单无静默跳过（每项三态齐全：结论/不适用+原因/
    待确认）；"待确认"项已汇总为开放问题并转 doc/md 功能提问文档——
    机检脚本：tools/arch_check.py；
  - 评审（**软门，推荐人审**）：方案对比与满性能推导评审。过门时
    明确提问"本门是否需要人工审核？"——需要则评审通过才过门；
    不需要则机检通过即过门。提问与决定记入过门提交信息。

### 阶段 2｜spec.yaml 提取（L1，正向提取，禁止 RTL 反推）

- 产物：`spec.yaml`（按 dv-collab `references/spec.md` 字段），每条
  FUNC/contract 带 `source`（文档条款号 + REQ-id）；registers 段属性
  用 RDL 词表（sw/reset/woclr/counter）语义对齐，一致性用机械对照
  脚本保证，不引入 SystemRDL；
- **G3 准出检查单**：
  - 机检（tools/spec_check.py 覆盖 a/c/d/e + 闭环对照）：a. schema
    校验（字段齐全、ID 唯一、引用闭合）；
    b. 可判定性（每条 FUNC = trigger→expected→observable；第一版靠
    评审+反模式清单，不做脚本）；
    c. A 层对照（文档条款↔FUNC 双向差集为空，或显式归
    out_of_scope/open_questions，见 §3）；
    d. REQ→FUNC 追溯（每 REQ 有 FUNC 覆盖；每 FUNC 挂 REQ 或标
    "设计细化"）；
    e. 接口事实机械对照（端口清单/寄存器地址与 reset/参数默认值
    ↔ RTL 提取一致，RTL 已存在时）；
  - 评审（**软门，推荐人审**）：spec 内容评审。过门时明确提问
    "本门是否需要人工审核？"——需要则评审通过才过门；不需要则
    机检通过即过门。提问与决定记入过门提交信息；
  - 过门动作：`doc.stage: draft→confirmed`、记录 `commit_id`，
    独立提交，交付验证侧。

### 阶段 3｜交付与维护（L1→L2 之间）

- 版本纪律（先升版再改码）、gap/question 回流、落地回填
  （dv-collab 已有机制，不新增）；QUE 闭环判据：答复被 spec 升版吸收
  （change_summary 引用 QUE-id）或标"无需升版"才允许关闭，spec
  open_questions 台账随升版同步增删（详见 dv-collab question.md）；
- 每次升版同样走"准出检查单（change_summary 与 diff 一致）+ 独立
  提交"；升版 change_summary 评审为软门，按审核分级提问决定；
- 设计文档更新按 §5 执行。

## 3. 功能点覆盖完整性：三层互查

完整性不靠单层保证，三层各抓一类遗漏。**职责划分：A 层是设计侧自检
（本 skill 职责——保证功能 yaml 产出正确且忠于文档）；B 层由验证侧
执行（其产物按 dv-collab 契约走 `gap.yaml` 回流设计）；C 层检查单
双方共用。**

- **A. 正向映射（文档→yaml，抓"写了但没提取/提取无源"）**：每条
  FUNC 的 `source` 回指文档条款；工具做**双向差集**——列出**未被
  任何 FUNC 引用的条款**（遗漏候选）与**无 `source`/`source` 失效
  （指向不存在条款）的 FUNC**（无源候选），逐条处置（补 FUNC / 补改
  source / 显式归 out_of_scope / open_questions）。语义级"曲解"
  （FUNC 偏离其 source 条款含义）机检判不了，靠 G3 评审与 B 层兜底；
- **B. 反向独立提取（第二视角，抓"设计者盲区"）**：验证侧收到 yaml 后
  先只看叙事文档**独立提取一遍功能点**，再与 yaml 对比；差异即遗漏或
  歧义——缺失走 `gap.yaml` 告知设计，歧义走 `question.yaml`。
  同一个人写的文档和 yaml 易共享盲区，独立视角才能打破；
- **C. 正交检查单 + VP 反挂（抓"忘了一整类"与"验证了规格外内容"）**：
  按 §4 十维逐条过，每维要么有条目要么显式写"无"；验证侧每个
  VP/checker 必须挂 FUNC-id——无 VP 的 FUNC = 验证遗漏，无 FUNC 的
  checker = 规格外判定（退回）。

## 4. 正交维度检查单（功能点提取时逐维过）

1. 每个接口的协议契约（信号表/时钟复位/协议/时序四要素逐接口）；
2. 每个寄存器/字段（reset 值、读写语义、清除行为）；
3. 数据通路主功能（每类事务逐个：读/写/各 burst 类型/窄传输/部分写/
   zero-mask…）；
4. 顺序与并发语义（保序规则、在飞数、背靠背有无气泡）；
5. 反压/流控（每个 ready 的行为契约与反压上限）；
6. 错误与异常路径（ECC、SLVERR、非法输入的约定行为）；
7. 边界与极值（最大 len、颗粒/4KB 边界、表项满、计数饱和、回卷）；
8. 性能相关可判定行为（posted 时机、反压点、满速条件）；
9. host 责任约束（显式列出"验证不判但激励必须遵守"的清单）；
10. out_of_scope 显式声明（防验证越界，也防"以为写了其实没写"）。

## 5. 设计文档更新与提问纪律

叙事文档是**活文档**：RTL 实现阶段与验证阶段都可能发现功能定义
模糊/矛盾、或规格层面的 bug，需要更新文档。纪律：

1. **先问后改**：AI 发现"功能需要更新"（文档模糊、文档与实现矛盾、
   验证回流问题涉及规格变化）时，**第一时间向人提问"是否需要更新
   设计文档"**，说明发现点与影响面；人不确认，不动功能性内容
   （typo/格式类修改不在此列）；
2. **确认后的更新顺序**：先改叙事文档（留修订记录）→ 升版
   `spec.yaml`（version + change_summary，先升版再改码）→ RTL/契约
   同步 → 相关 question/gap 条目闭环回填；
3. **触发源**：设计实现自查发现、question.yaml 回流（歧义答复被
   吸收）、bug.yaml 判 spec_ambiguity、gap.yaml accepted 落地；
4. **留痕**：文档更新独立成 commit，`change_summary` 与实际 diff
   一致；升版评审为软门，按 §2 审核分级提问决定。

## 6. 架构设计方法（原 hw-arch-design，2026-08-19 融入）

做架构方案、模块划分、接口设计时遵循
[`references/arch-design.md`](references/arch-design.md)——做该类工作
前**必读全文**。核心原则：

- **先问清再设计**：结构化提问（只问缺的、给默认值、一次≤4 个）；
- **性能与功能同为一等公民**：先性能模型（数字）后模块划分（图纸）；
- **分析检查单按设计形态裁剪**：逐项只有三态（定量结论 / 不适用+原因 /
  待确认），不许静默跳过。

阶段 0 的结构化提问与 G2 机检的"检查单三态"即按该文件执行。

## 7. RTL 代码风格（原 sv-rtl-style，2026-08-19 融入）

生成、修改或 review SystemVerilog RTL 代码时遵循
[`references/rtl-style.md`](references/rtl-style.md)——动手写/改 RTL 前
**必读全文**。涵盖：文件结构、`#0.1` 时序、always_ff/always_comb 拆分、
generate for 寄存器组（Verilator 单进程 for 缺陷规避）、显式位宽、
握手纪律（其 §5：valid/ready 默认完全独立、offer/fire 分离）、命名
（`_q`/`_c`/`_n`、存储一律 fifo）、注释风格。review 必查 `_q`/`_c`
名实相符。
