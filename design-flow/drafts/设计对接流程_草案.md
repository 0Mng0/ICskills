## 总设计：四件套

1. **阶段模型**：L0 需求规格 → L1 开发 → L2 签核（对齐 OpenTitan，
   裁剪到模块级）；
2. **准出检查单**：每个阶段门一张，分机检项（脚本可判）与评审项
   （人判），逐条给结论，不许静默跳过；
3. **独立提交过门**：每次过门 = 一次专门的 git 提交（不夹带其他改动），
   提交信息列检查单逐条结果与依据——评审即审查该提交；
4. **commit 锚定**：过门点在 `spec.yaml` 的 `doc` 区记录 `stage` 与
   `commit_id`，任何时刻可重建"哪版规格对应哪版代码"。
5. **审核分级（2026-08-19 用户定）**：**G1 为硬门，必须人审**，机检全过
   不豁免；**G2/G3 为软门，推荐人审**——过门时必须向用户**明确提问**
   "本门是否需要人工审核？"：需要则评审通过才过门；不需要则机检通过
   即过门。提问与用户的决定必须记入该次过门提交信息（防静默跳审）。

阶段状态机（记录在 spec.yaml `doc.stage`）：

```
draft ──G1──▶ req_confirmed ──G2──▶ arch_reviewed ──G3──▶ confirmed（交付验证侧）
  （G1 需求确认 / G2 架构评审 / G3 spec 签版；confirmed 后变化走升版流程）
```

## 阶段 0｜需求收集（L0，与设计人员对话）

- 动作：设计人员提供设计功能（口述/草稿），按 hw-arch-design §2
  结构化提问（只问缺的、给默认值、一次≤4 个）；
- 产物：叙事文档第一章"需求清单"：每条需求一个 REQ-id（REQ-001…）、
  来源、优先级；默认值/假设显式列出；
- **G1 准出检查单**：
  - 机检：每条 REQ 有 id/来源/优先级；无"等/若干/尽量"类模糊词；
    假设清单存在且逐条有处置（确认/转 question.yaml）；
  - 评审（**硬门，必须人审**）：设计人员确认默认值与假设——机检
    全过不豁免，人审通过才过门。

## 阶段 1｜架构设计（L0→L1，hw-arch-design 全流程）

- 产物：叙事设计文档（方案对比+定量推导+模块划分）；
- **G2 准出检查单**：
  - 机检：分析检查单无静默跳过（每项三态齐全：结论/不适用+原因/
    待确认）；"待确认"项已汇总为开放问题并转 question.yaml；
  - 评审（**软门，推荐人审**）：方案对比与满性能推导评审。过门时
    明确提问"本门是否需要人工审核？"——需要则评审通过才过门；
    不需要则机检通过即过门。提问与决定记入过门提交信息。

## 阶段 2｜spec.yaml 提取（L1，正向提取，禁止 RTL 反推）

- 产物：`spec.yaml`（按 dv-collab `spec.md` 字段），每条 FUNC/contract
  带 `source`（文档条款号 + REQ-id）；registers 段属性用 RDL 词表
  （sw/reset/woclr/counter）；
- **G3 准出检查单**：
  - 机检：a. schema 校验（字段齐全、ID 唯一、引用闭合）；
    b. 可判定性（每条 FUNC = trigger→expected→observable）；
    c. A 层对照（文档条款↔FUNC 映射差集为空，或显式归
    out_of_scope/open_questions）；
    d. REQ→FUNC 追溯（每 REQ 有 FUNC 覆盖；每 FUNC 挂 REQ 或标
    "设计细化"）；
    e. 接口事实机械对照（端口清单/寄存器地址与 reset/参数默认值
    ↔ RTL 提取一致，RTL 已存在时）；
  - 评审（**软门，推荐人审**）：spec 内容评审。过门时明确提问
    "本门是否需要人工审核？"——需要则评审通过才过门；不需要则
    机检通过即过门。提问与决定记入过门提交信息；
  - 过门动作：`status: draft→confirmed`，独立提交，记录 commit_id，
    交付验证侧。

## 阶段 3｜交付与维护（L1→L2 之间）

- 版本纪律（先升版再改码）、gap/question 回流、落地回填
  （dv-collab 已有机制，不新增）；
- 每次升版同样走"准出检查单（change_summary 与 diff 一致）+ 独立提交"；
- 软门：升版 change_summary 过评审。

## 三性质映射

- **可验证**：G1~G3 机检项可脚本判；评审项客观化（检查单逐条结论）；
- **可追溯**：`REQ-id → 文档条款 → FUNC-id.source → VP → BUG/GAP →
  commit`，过门点由 doc.stage+commit_id 锚定；
- **人审查**：G1 硬门 = 必须人审；G2/G3 软门 = 显式提问决定是否人审，
  决定与理由记入过门提交。AI 不批准自己的产出：硬门必须由人确认；
  软门放弃人审是用户的显式决定，必须留痕，不许默认跳过。

## 待定项（用户待确认）

1. REQ 管理方式：建议嵌叙事文档（REQ-id 清单）不单独建 yaml；
   需求另有正式出处时 REQ-id 直接引用外部编号；
2. 机检脚本范围：第一版做 a/c/d/e，b（可判定性）靠评审+反模式清单；
3. spec.yaml `doc` 区是否加 `stage/commit_id` 字段（需改 dv-collab
   spec.md 契约——这是唯一波及契约的改动）。
