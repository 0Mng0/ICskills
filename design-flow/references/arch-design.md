# 硬件架构设计方法

适用于数字电路架构设计（数据通路、控制器、总线接口、计算单元、存储系统等）。
核心原则：**先问清再设计；性能与功能同等重要；分析项按需裁剪但不许静默跳过**。

## 1. 第一步：判断设计形态（决定后续哪些分析适用）

开工先花一分钟归类，不需要用户输入时自行判断并声明：

- **设计类型**：数据通路型 / 控制主导型 / 接口桥接型 / 计算单元型 / 混合型；
- **时钟域**：单时钟还是多时钟（决定是否需 CDC 分析）；
- **共享资源**：是否存在多主争用（单端口存储、共享总线、仲裁器）；
- **数据速率阶梯**：上下游各级速率是否匹配（决定是否需要缓冲分析）；
- **主要优化轴**：吞吐 / 延迟 / 面积 / 功耗，哪个排第一。

## 2. 第二步：结构化提问（只问缺的，给默认值，不追问到底）

规则：

- **只问设计文档/对话里还没有的信息**，已知的不要重复问；
- **分批少量**，一次最多 3~4 个问题，每个问题附**推荐默认值**（如"带宽敏感还是延迟敏感？默认带宽敏感"）；
- 用户不答或说"你看着办"→ 采用默认值，**在方案开头显式列出全部假设**，请用户事后确认；
- 典型必问项（视形态裁剪）：
  - 性能验收：目标吞吐/频率/位宽？满带宽是否是硬指标？事务间允许气泡吗？
  - 上下游行为：协议信任边界（哪些合法性由对方保证）？流量模型（读写比、burst 长度分布）？
  - 约束：面积/功耗优先级？参考实现或业界惯例锚点？

## 3. 输出模板（架构文档章节，按形态裁剪）

1. 需求与性能指标（定量；含 §2 确认的假设清单）；
2. 候选方案对比：每个方案给结构、数据流、**满性能条件推导**、优缺点；
3. 数据流：各方向逐模块经过什么、做什么；
4. 定量分析（见 §4，只保留适用项）；
5. 模块划分与接口定义（信号级）；
6. 资源/面积粗估；
7. 风险与待确认项（外部依赖单列）。

顺序要求：**先性能模型（数字）后模块划分（图纸）**。

## 4. 分析检查单（按 §1 形态裁剪）

执行规则：**每一项只有三种合法状态——给出定量结论 / 标注"不适用"+原因 / 标注"待确认"。不允许静默跳过。**

| 项 | 适用条件 | 要回答的问题 |
|---|---|---|
| 事务间气泡 | 有握手接口 | 相邻事务间有没有空闲拍？ready 链是否跨模块组合？**命令与返回两个方向分别推导**：每级"数据拍数/事务拍数"≥目标速率比吗？（只算发送侧会漏掉返回侧的隐藏瓶颈） |
| 握手体制 | 有握手接口 | 接口有无 ready？无 ready → 必须 credit（发命令前验证响应有槽可放）；有 ready → 反压保正确、buffer 只保性能；**禁止用"预留槽"补丁 ready 协议**（防不了非合规源，且与握手语义冲突） |
| 速率差缓冲 | 存在速率阶梯 | 生产者>消费者的每处接口，buffer 深度 ≥ 单个最大事务？反压堵谁？深度按体制定：**无 ready/credit 制须覆盖"在途=延迟×速率"；有 ready 制只需握手平滑余量（几拍），大 buffer 放高带宽一侧** |
| 跨时钟信用 | 多时钟域 | 异步 FIFO/握手深度 ≥ RTT×消费速率？ |
| 保序/重排 | 有顺序要求 | 缓冲量与头阻塞代价？最慢路径撞队首的影响？ |
| 计数器健康 | 有计数器/在途跟踪 | 会回绕吗（回绕即判据失效，需上限门控）？门控用途是防溢出还是性能（注释写明）？能否用 FIFO 自身状态（wready/almost_full）替代计数器？ |
| 串行化点 | 有共享资源/状态机 | "一次一个事务"的环节，服务时间×到达率 < 1 吗？ |
| 状态机边界 | 带宽敏感通路 | **考虑带宽时不要用状态机**：逐事务 FSM 的"每事务拍数 > 每事务数据拍数"即带宽损失；满带宽数据通路用"流水寄存器+握手"（当前事务末拍同拍装载下一事务）；FSM 仅用于真正的多阶段串行序列（RMW、初始化、错误处理等） |
| 仲裁位置 | 有争用 | 仲裁点是否紧贴被共享资源？经过 CDC/FIFO 后顺序仍有效吗？ |
| 慢事件摊薄 | 存在周期性/偶发慢操作（刷新、RMW、错误处理） | 慢事件期间其余通路能否继续？占比多少？ |
| 反压路径 | 有缓冲 | 每级满时反压谁？会否经共享通道堵死无关流量？ |
| 流水级数 | 高频设计 | 每级逻辑深度可收敛吗？打拍位置是否切断跨模块长路径？ |

无共享资源、单时钟、速率匹配的简单设计，大部分项会标"不适用"——这是预期结果，裁剪本身就是分析结论的一部分。

## 5. 默认假设（除非用户另说）

- 以满性能（满带宽/零气泡）为目标设计；性能损失必须显式声明并量化；
- 功能正确性不依赖 buffer 深度（深度只影响性能）；
- 对方该保证的协议合法性写进系统规格书，不加冗余硬件检查；
- 共享资源利用率是首要优化对象。
